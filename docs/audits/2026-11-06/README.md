# Falcon Fuel: product and engineering audit · November 6, 2026

**Decision:** Keep the existing Today → choose → check in → history experience. Gate broader release of personalized live dining on three fixes: restrictions must respect missing allergen evidence, a menu must match the requested service date before the app presents it as available, and the pinned Next.js release needs a reviewed security update. The first two gates can be met by withholding unsupported claims while continuing to offer clearly labeled browsing and manual logging. No student exposure, compromise, or incident was established by this audit.

[Prioritized findings and acceptance tests](FINDINGS.md) · [Implementation roadmap and first ten tasks](ROADMAP.md) · [Verification record, reproductions and scope](EVIDENCE.md). The findings document is the inventory; the roadmap sequences it rather than creating a second set of requirements.

## A. Executive diagnosis

Falcon Fuel has a working student journey. A student can onboard without supplying body measurements, pick a dining location, select a meal, choose a portion, and check in on what they actually ate. The pending state correctly separates a selection from consumption. Canonical logging, composed meals, dated plans, editable history, export/import, mobile overflow fixes and retrospective date handling already exist on main. Rebuilding them or merging old feature branches wholesale would put working behavior at risk. The app also has a useful distinction between demo and sourced menus and meaningful tests for the core meal logic.

The largest weakness is what the product means by **verified**. A trusted admin can publish a real menu from yesterday. A real dish can lack allergen information. A correctly named food can have estimated nutrition. Those are three independent facts, yet a single label or missing array can make the record look suitable for a recommendation today. Once selected, the meal becomes a saved snapshot, so fixing tomorrow’s feed cannot correct the impression on yesterday’s log. Fix the claims at ingestion **and** where a student decides what to eat. Never rewrite past consumption from today’s catalog.

The second weakness is that several workflows construct food IDs, line totals and quality labels differently. Food logging is implemented, but a removal can fix calories while leaving fiber and sodium doubled. At Falcon Market a route can lose the intended date before the user saves. Both produce credible-looking personal records that mean the wrong thing. These deserve attention ahead of more scoring rules, animation or gamification.

The app is a useful **single-browser product**, not a student account system. GitHub sign-in protects the dining publisher; it does not back up a student's meals. Browser storage supports a low-friction guest experience, including export and restore, but clearing a browser or moving to another device breaks continuity without a backup. Make this boundary visible now; build optional accounts only when ownership, migration and deletion are designed together.

## D. Architecture and product recommendations

**What ships today.** Next.js App Router and React serve a Vercel application. TypeScript services do most normalization, recommendation scoring, meal arithmetic and validation. Server components load dining catalogs; client components personalize them and write to browser repositories. A daily bearer-protected refresh and an allowlisted GitHub/Auth.js admin publication path supplement public dining reads. Dated menus and a “current” pointer use a memory/shared runtime-cache repository. There is no application student database, cloud student identity, or server copy of a student’s history in the reviewed implementation.

| Boundary | What happens now | Contract to adopt |
|---|---|---|
| Source → menu | Eight configured upstream outlets map to six Bentley physical locations; Falcon Market is an additional demo catalog. Feed discovery, manual 921 capture and mock fixtures have different evidence. | Keep a single adapter interface. Record outlet, campus service date, period, revision, source, coverage, capture time and retrieval time. Distinguish closed, unpublished, partial, blocked and unavailable. |
| Publication → availability | A trusted “current” pointer can precede a dated match. A date shown in the UI can come from the request rather than the data. | Make availability a pure decision on outlet/date/period. Never mutate current on ordinary reads. A clearly dated “last published” view is useful even when unavailable for the requested meal. |
| Menu → recommendation | Restrictions rely on matching known allergen lists. Candidate construction, normalization and presentation differ between Today and the builder. | Assess restriction coverage before scoring. Share candidate preparation and eligibility across entry points. Show provenance for the chosen item, not a global success badge from another outlet. |
| Food → offering → meal | Station/date/name, upstream item IDs and snapshot IDs serve different purposes, sometimes in the same field. | Separate stable food or recipe identity, dated offering identity and unique logged-line identity. Record portion, nutrient units, evidence and quality in an immutable as-eaten snapshot. A repeat can point to the same food without claiming it is offered now. |
| Meal → day → history | Creation, editing, planning and check-in can use separate reducers or writes. | One reducer for line totals and quality; one transition for fulfilling a plan. Count consumption only after check-in; apply completion and portion scale once. Keep uncertain legacy values visibly uncertain. |
| Student → storage | Profile, plans, history and progress mostly live in browser storage; admin auth has a separate purpose. | Keep guest mode. For optional accounts, add independent student identity, per-owner authorization, revision and idempotency rules, restore/export and deletion before enabling sync. |

**Sustainable dining data.** [Bentley’s dining page](https://www.bentley.edu/university-life/housing-dining/dining) is the student-facing starting point for menus and dietary support. It does not establish permission for bulk automated access or republication. The product owner should agree with Bentley/dining operator on a supported feed, allowlisted integration or scheduled licensed export; confirm outlets, service dates/time zone, portions and nutrient units, allergen coverage, correction procedures, attribution, retention and an operational contact. Ask for examples covering closures, partial days and revised menus. Until then, use only authorized manual imports; on a failed refresh show the last publication with its date or link to the official menu. Keep generic logging available. Do not invest in defeating an upstream challenge.

**Student-facing priority.** Preserve the dark mobile shell, source labels, plain-language meal choices, optional onboarding fields and pending check-in. Improve the decisions that immediately precede a save: “Offered for lunch today”, “Last published Tuesday”, “Allergen information unavailable”, “Estimated nutrition”, and “Saved for Friday” mean different things. A recent food should be quick to log even when it is unavailable to order. Build verified discovery, repeat logging and coverage-aware progress on that distinction. Place cross-device sync, institution-level reporting and native distribution behind separate product decisions.

**Limits on the decision.** The inventory distinguishes deterministic source defects, observed behavior, exposure that depends on deployment, and proposed capabilities. The mobile session used an isolated local build. The audit did not publish a menu, test real student data, exercise a provider challenge, inspect production secrets, perform a penetration test, measure field latency, or establish dietary safety. See the verification record before interpreting test totals or availability claims.
